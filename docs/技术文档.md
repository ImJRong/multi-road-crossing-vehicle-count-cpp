## 零、概述

板端实现。读监控视频，检测车辆，跟踪发编号，穿过计数线时按方向计数。

和 Python 版是两套独立代码，共用同一份模型和同一套配置文件：

| | Python 版 | C++ 版 |
|---|---|---|
| 推理 | ultralytics | ONNX Runtime（PC）/ RKNN（板子） |
| 跟踪 | ultralytics 内置 ByteTrack | 自实现：卡尔曼预测 + 匈牙利分配 + 两阶段关联（代价 1-IoU，阈值 0.8 / 0.5） |
| 用途 | 调参、验证算法、出报告数据 | 板子上跑 |

### 一、现在是什么状态

| 项 | 状态 |
|---|---|
| RKNN 推理（INT8） | 18.3 fps |
| **框定位精度** | **中心偏移 0.03 px（原 6.75 px）** |
| 网页实时显示 | MJPEG 推流 |
| 跟踪 + 过线计数 | 能跑 |
| 参数实时调整 | 网页改 conf/iou 立即生效 |
| 四路并行分屏 | `traffic_web_quad`，四路各 20 fps（板端实测） |
| 系统状态显示 | CPU / 温度 / NPU 频率 / 三核负载 |

#### 框偏移已解决

板端框原先整体偏左上 6～22 px，车越小偏得越多。现已修复，速度不变。

RKNN 按 `范围/256` 分配量化刻度。原模型输出坐标（0～640），刻度 2.5；而 DFL 内部的距离只有 0～15，被粗刻度压没了精度。改法是把模型输出换成「DFL 距离 0～15」，坐标换算移到 `rknn_detector.cpp` 用 float 完成。距离成为独立输出后，RKNN 按其真实范围分配刻度 0.047，精细 53 倍。

模型权重一个字节未改，量化方式未改，速度未变。

> 完整原理（量化机制推导、11 张图）见 Python 版仓库 `docs/head4_原理详解.md`。

#### 计数漏

转弯车曾经常漏计。实测定量结果：改用 head4 后断号减少 34.3%（12135 帧，2559 → 1680 个轨迹编号），计数净增 12，无一条线下降。

框偏移导致的框抖确实是漏计的一个成因，但只解释了约三分之一。剩余成因未进一步查证，投入产出比不高，暂告一段落。

> `count_dir` 只统计一个方向属设计意图：这几个路口均为单行道。

### 三、编译

依赖 OpenCV，外加 ONNX Runtime（PC）或 librknnrt（板子）。

**PC 上（ONNX Runtime）**

```bash
cmake . && make
```

**板子上（RKNN）**

```bash
cmake . -DUSE_RKNN=ON -DRKNN_ROOT=/usr && make
```

`RKNN_ROOT` 目录下要有 `include/rknn_api.h` 和 `lib/librknnrt.so`。板子上这两个分别在 `src/` 和 `/usr/lib/`，所以编译时还要 `-Isrc`。

换了 `CMakeLists.txt` 里的路径之后必须删掉 `CMakeCache.txt` 再 cmake：

```bash
rm -f CMakeCache.txt && cmake . -DUSE_RKNN=ON && make
```

`set(... CACHE ...)` 不会覆盖缓存里的旧值，不删就一直用老路径。

编出来三个可执行文件：

| 文件 | 用途 |
|---|---|
| `traffic_count` | 命令行版，跑完退出 |
| `traffic_web_single` | 网页版，常驻等命令 |
| `rknn_probe` | 模型体检（只在 `USE_RKNN=ON` 时编） |

### 四、运行

#### 命令行版

```bash
./traffic_count test4     # 跑 test4 配置
./traffic_count           # 不带参数，列出现有配置
```

配置读 `configs/testN.json`，视频读配置里写的路径，模型读 `models/best_detrac.onnx`（RKNN 版读 `.rknn`）。

`configs/*.json` 里的 `output` 三种取值：

| 值 | 行为 |
|---|---|
| `"save"` | 写 mp4 到 `output/` |
| `"none"` | 纯推理测速，不写不显示（板子上最常用） |
| `"show"` | 板端崩溃（无显示器，GTK 初始化失败） |

#### 网页版

```bash
./traffic_web_single 8080
```

浏览器打开 `http://<板子IP>:8080`，选配置点「开始」。MJPEG 推流，是板子上唯一能看实时画面的方式。

测完需关闭，否则一直占用 8080：

```bash
pkill -f "[t]traffic_web_single"
```

`[t]` 这个写法不能省。`pkill -f traffic_web_single` 会把自己那条命令也匹配上，一起杀掉。

#### CPU 调频（影响帧率，重启失效）

默认 `ondemand`，同一段 400 帧实测 15.6 fps；设 `performance` 后 20.6 fps：

```bash
for p in /sys/devices/system/cpu/cpufreq/policy*; do
    echo performance | sudo tee $p/scaling_governor
done
```

### 五、配置在哪改

| 想改什么 | 改哪里 | 改完要做什么 |
|---|---|---|
| 工程根目录、库路径 | `CMakeLists.txt` | 删 `CMakeCache.txt` → `cmake . && make` |
| 视频、ROI、计数线、conf、iou、imgsz | `configs/testN.json` | 不用编译，直接跑 |
| 跟踪器内部阈值 | `configs/testN.json` 的 `track` 段 | 不用编译，直接跑 |

#### 参数一览

**在 json 里（不用编译）**

| 参数 | 典型值 | 作用 |
|---|---|---|
| `imgsz` | 640 | 送进模型的边长，必须和模型导出时一致 |
| `conf` | 0.1 ～ 0.4 | 检测的最低分。降到 0.1 才能让跟踪的第二轮工作 |
| `iou` | 0.3 ～ 0.5 | NMS 阈值。太小会把并排的车合成一辆 |
| `lines[].margin` | 6 ～ 10 | 死区（像素）：离线这么近不判过线，防车压线抖动反复计数 |
| `lines[].count_dir` | `"pos"` / `"neg"` / 不写 | 只数一个方向。不写 = 两个方向都数 |
| `track.high` | 0.45 ～ 0.50 | 高分框下限，够格的框才能建新轨迹 |
| `track.low` | 与 `conf` 相同 | 低分框下限。配得比 `conf` 低没有意义，那些框到不了跟踪器 |
| `track.new` | 与 `high` 相同 | 建新轨迹门槛。只在高分堆里判，等于 `high` 时无实际作用 |
| `track.match` | 0.8 | 第一轮代价上限（代价 = 1 − IoU），0.8 相当于 IoU ≥ 0.2 |
| `track.buffer` | 30 | 轨迹丢失后还保留几帧（30 帧约 1.2 秒 @24fps） |

**在代码里（要重新编译）**

| 参数 | 值 | 位置 |
|---|---|---|
| `kMinTravel` | **35** | `tracker.hpp`，位移小于它算静止目标，既不计数也不画框 |
| 第二轮代价上限 | 0.5 | `tracker.cpp`，≈ IoU 0.5，与 ultralytics 一致 |

`tracker.hpp` 里 `Tracker` 构造函数的默认参数是 0.45 / 0.30 / 0.45 / 0.8 / 30，只在配置没写 `track` 段时生效。

第二轮匹配的阈值 0.5（≈ IoU 0.5）是硬编码的，和 ultralytics 一致：低分框不可靠，位置必须高度吻合才敢认。

### 六、模型转换

#### 唯一验证通过的配方

| 项 | 值 |
|---|---|
| 工具 | **rknn-toolkit2 1.6.0+81f21f4d**（2.5.0 不可用于转换，见下文） |
| 输入 ONNX | `best_detrac_head4.onnx`（删掉末端 Concat + DFL 之后的 9 个换算节点） |
| ONNX 输出名 | `/model.22/dfl/Reshape_1_output_0`（距离 `[1,4,8400]`）+ `/model.22/Sigmoid_output_0`（分数 `[1,1,8400]`） |
| config | `target_platform='rk3588'`、`mean_values=[[0,0,0]]`、`std_values=[[255,255,255]]` |
| build | `do_quantization=True`，其余全默认（w8a8 / normal / optimization_level 默认 1） |
| 校准集 | 300 张，每个视频各 75 张 |
| 产出 | `models/best_detrac.rknn`，**5,969,848 字节** |
| 关键指标 | 距离输出的 `scale = 0.046943`（旧模型是 2.5017） |

输出距离而不是坐标，是因为 RKNN 按 `范围/256` 分配刻度：输出坐标（0～640）刻度 2.5，输出距离（0～15）刻度 0.047，精细 53 倍。坐标换算（`anchor ± 距离`，再乘 stride）移到 `rknn_detector.cpp` 用 float 完成。

> 详细推导见 Python 版仓库 `docs/head4_原理详解.md`。

#### 换模型不用改代码

`rknn_detector.cpp` 按输出张量名里有没有 `"dfl"` 自动识别模型类型：

```cpp
// head4: /model.22/dfl/Reshape_1_output_0  -> 含 "dfl"，走距离换算
// head3: /model.22/Mul_2_output_0          -> 不含，直接用坐标
impl_->boxes_is_dist = std::string(a.name).find("dfl") != std::string::npos;
```

因此 `best_detrac.rknn` 换成 head3 或 head4 都能直接跑，无需重新编译。

#### 为什么不能用 Split 拆输出头

原 ONNX 的 `output0` 是 `[1,5,8400]`，末端一个 Concat 把坐标（0～640）和分数（0～1）拼在同一个张量里。INT8 是每个张量一套量化参数，量程被坐标撑到 640 后分数全被舍成 0，所以必须拆。

拆法有两种，只有一种能用：

| 拆法 | 图结构 | 结果 |
|---|---|---|
| 失败：在 Concat 后面加 Split | `Concat_3 → output0 → Split → boxes/scores` | 1.6.0：scores 的 8400 个 int8 全是 `-128`（= zp = 0.0）；2.5.0：分数正常但框塌 |
| 成功：删掉 Concat | `Mul_2 → boxes`、`Sigmoid → scores` 直接当输出 | 1.6.0 转出来正常 |

原因是 RKNN 编译器会把挂在输出上的 Split 融合掉，两个版本各有各的融错法。删掉 Concat 就没有可融的东西。

脚本自带校验：把两路输出拼回去和原模型 `output0` 逐元素比，最大差值必须是 0。

#### 复现

```bash
# Windows 侧：生成 ONNX（每步都带校验）
D:\Python3.12.4\python.exe tools\01_convert\make_head3.py
D:\Python3.12.4\python.exe tools\01_convert\make_head4.py
D:\Python3.12.4\python.exe tools\01_convert\verify_head4_decode.py   # 必须看到差值 0

# WSL 侧：转 RKNN
conda activate rknn16
cd ~/traffic_count
python /mnt/d/multi-road-crossing-vehicle-count/tools/01_convert/convert_head4_probe.py
```

#### 为什么不能用 rknn-toolkit2 2.5.0

同一份 ONNX、同一批校准图、同一套 config，只换工具版本：

| 工具 | 结果 |
|---|---|
| 1.6.0 | 框正常 |
| 2.5.0 | **w/h 被放大 13 倍**，通道最大值顶到 637.92（= 255 × 2.5） |

2.5.0 的 `auto_hybrid`（自动混合量化）开关本身正常，但救不了这个缺陷。

#### 试过但没用的

- `quantized_dtype`、`hybrid_level`、`custom_string`、`quantized_input_type` —— 都是猜的，无效
- `mmse` / `kl_divergence` —— 只是换裁剪范围，1 像素级收益；mmse 还容易 OOM
- `optimization_level=3` —— 把 DFL 的归一化融没了，坐标算出天文数字（`cx = -2.18e33`）
- 各种混合量化方案 —— 两个工具版本都不通

### 七、模型体检：rknn_probe

换新模型先跑它，别拿业务程序猜。

```bash
cd ~/code
make rknn_probe                                            # 只编它，几秒钟
./rknn_probe models/新模型.rknn data/videos/test1.mp4 200
```

它打印每个输入/输出张量的形状、类型、`scale`、`zp`，然后真跑一帧，把输出原样摊开：反量化后的 float 加未换算的 int8。

#### 合格标准

**head4（当前）**

| 输出 | 合格表现 |
|---|---|
| 距离 float | min ≈0、max ≈11、**均值 ≈2.4** |
| 距离 scale | **0.046943**（这是方案成立的关键指标） |
| scores int8 | 8400 个里约 **60 个非零、9 个 >0.5** |

**head3（对照）**

| 输出 | 合格表现 |
|---|---|
| boxes float | min 0、max ≈630、**均值 ≈182**（塌了会变成 330 左右） |
| boxes scale | 2.501652 |
| scores float | max ≈0.78～0.80 |

**一眼判据**：看 `[OUT1 int8]` 那行的 `==zp(-128)`——**8340 左右 = 好；8400 = 全 0，模型坏了**。

8400 个候选框里绝大部分本来就是背景，所以「几乎全是 -128」是正常的。

判断 4 个通道有没有坏，用 `tools/02_diagnose/ch_scan.cpp`：

```
正常: ch0 0~630 | ch1 0~615 | ch2 2.5~510 | ch3 2.5~230   （四路各不相同）
坏了: 四路全是 0~638                                        （= 255 × 2.5，被截断）
```

### 七点五、批量评测：multi_eval

`rknn_probe` 只看一帧，`multi_eval` 跑完整视频并给出计数统计，用来量化比较两个模型的差别。

和 `traffic_count` 的区别是不画框、不存视频、可多路并行，所以快得多。单路 18～22 fps，四路并行合计 62～73 fps。

```bash
cd ~/code
make multi_eval

# 四路并行，各跑前 3600 帧（视频更短的跑完即止）
./multi_eval configs/test1.json configs/test2.json configs/test3.json configs/test4.json \
    --frames 3600 --out output/full_head4

# 换模型对比同一批数据
./multi_eval configs/test1.json configs/test2.json configs/test3.json configs/test4.json \
    --frames 3600 --model /path/to/other.rknn --out output/full_other
```

参数：

| 参数 | 作用 |
|---|---|
| `--frames N` | 每路最多跑 N 帧，0 或不写 = 全部 |
| `--model path` | 指定 `.rknn` 模型，默认 `models/best_detrac.rknn` |
| `--out prefix` | 结果写到 `<prefix>_summary.csv` |

实现上每个线程创建独立的 `RknnDetector`，按 `i % 3` 绑定到 0/1/2 号 NPU 核（`RknnDetector::set_core()`），四路线程才真正分散到三个核上并行。

结果 CSV 用 `tools/02_diagnose/compare_models.py` 对比，输出断号数和各线计数。

#### 实测结果

完整视频（12135 帧），v7 与 head4 同配置对比：

| 视频 | 帧数 | v7 编号数 | head4 编号数 | 降幅 |
|---|---|---|---|---|
| test1 | 3600 | 553 | **450** | 18.6% |
| test2 | 3600 | 625 | **441** | 29.4% |
| test3 | 2535 | 909 | **539** | 40.7% |
| test4 | 2400 | 472 | **250** | 47.0% |
| **合计** | 12135 | **2559** | **1680** | **34.3%** |

编号数是 `Tracker::total_ids()`，即累计分配过多少轨迹编号。同一视频同样帧数下，编号越少说明断号越少（一辆车被反复换号）。计数变化净增 +12，无一条线下降。

框偏移修复让断号减少约三分之一，这部分漏计随之解决；剩余漏计另有成因（见第一节「计数漏」）。

### 七点六、性能实测：pipeline_bench

单视频流水线，并行推理加串行跟踪，三段之间用队列连接，帧号作钥匙。

```
读帧线程 ──→ 队列 ──→ K 个推理线程 ──→ 队列 ──→ 跟踪线程
```

### 八、跟踪算法

自己实现的 ByteTrack，一帧的流程：

```
① 卡尔曼给每条轨迹预测位置
② 检测框按分数分两堆：>= high 高分，low~high 低分（两个值都在 json 的 track 段）
③ 第一轮：所有轨迹 × 高分框 → 匈牙利分配
④ 第二轮：第一轮没配上的 Tracked 轨迹 × 低分框 → 匈牙利
⑤ 高分框没人认领的 → 建新轨迹；低分框没人认领的 → 丢弃
⑥ 两轮都没配上的 → lost+1，超过 30 帧删掉
```

几处易错点：

- 低分框不能建新轨迹。树影、反光、广告牌边缘都在低分里，让它们开新户，一帧能冒出十几个假 ID
- Lost 状态的轨迹仍要参与第一轮，否则「留着等它回来」是空话
- 匈牙利求出的是完美匹配，必须再剔除代价超阈值的配对，否则所有轨迹都会配上
- 输出框用卡尔曼滤波后的状态（`kf.state()`），不必再叠加 EMA——属重复平滑，额外增加 1～2 帧滞后（2026-11-01 删除）

和 ultralytics 的差别在于卡尔曼状态的定义：ultralytics 用 XYAH（中心 + 宽高比 + 高），这里用 XYWH。数学等价，只是参数化不同。

### 八点五、跟踪阈值实测

`conf` 与跟踪器的 `high` 是两道串联的筛子：`rknn_detector.cpp` 先按 `conf` 扔框，`tracker.cpp` 再按 `high` / `low` 分堆。`conf` 高于 `high` 时低分堆永远为空，ByteTrack 的第二轮补救全程空转。四个视频原配置都是 `conf = 0.3`，所以 `low` 配 0.1 还是 0.30 进来的是同一批框。

**分数分布**（FP32 模型，`conf = 0.001` 全捞，每 10 帧取 1 帧）：

| 视频 | 采样帧 | 框数 | P50 | P90 |
|---|---|---|---|---|
| test1 | 1082 | 28294 | 0.127 | 0.860 |
| test2 | 2725 | 121032 | 0.011 | 0.815 |
| test3 | 254 | 8145 | 0.456 | 0.881 |
| test4 | 240 | 8711 | 0.038 | 0.790 |

45%～52% 的框分数低于 0.05，属背景误报；真车集中在 0.5 以上（P90 均在 0.79～0.88）。0.1～0.3 区间只占全部框的 1%～2%，真车与误报混杂，没有干净的分界。因此降低 `conf` 换召回不可行：实测把 `conf` 调到 0.1 后，栅栏、摩托车、广告牌、地面箭头全部被判成车。

**阈值对比实验**（四路并行，每路 3000 帧，共 10935 帧，单轮约 160 秒）：

| high / low / new | test1 | test2 | test3 | test4 | 编号合计 | 计数合计 |
|---|---|---|---|---|---|---|
| 0.25 / 0.10 / 0.25（原默认） | 393 | 365 | 539 | 250 | 1547 | 836 |
| 0.35 / 0.30 / 0.35 | 358 | 327 | 536 | 245 | 1466 | 831 |
| 0.40 / 0.30 / 0.40 | 332 | 279 | 515 | 240 | 1366 | 831 |
| 0.45 / 0.30 / 0.45 | 303 | 254 | 506 | 234 | 1297 | 831 |
| 0.50 / 0.30 / 0.50 | 280 | 228 | 498 | 223 | 1229 | 830 |
| 0.50 / 0.10 / 0.50 | 280 | 228 | 498 | 223 | 1229 | 830 |

编号数越少表示同一辆车被换号的次数越少，计数合计为四条计数线之和。

三条结论：

1. `high` 从 0.25 提到 0.50，编号数下降 20.6%（1547 → 1229），计数只掉 0.7%（836 → 830）。
2. 最后两行结果完全一致，证明 `low` 在 `conf = 0.3` 下不起作用，应当直接配成与 `conf` 相同。
3. `new` 只在高分堆内判定，而高分堆的定义就是 `>= high`，所以 `new = high` 时该判断恒不成立。

**当前取值**：`high` 0.50（test1/2/4）、0.45（test3），`low` 0.30，`new` 与 `high` 相同，`match` 0.8。test3 取 0.45 是因为 0.50 会掉 1 个计数（A 线 240 → 239）。每个视频可在 `configs/testN.json` 的 `track` 段单独调整。

### 九、计数逻辑

`counter.cpp` 的 `update()`，一辆车每帧调一次：

1. `near_segment(p, a, b, margin)` —— 点落不落在这条线这一段上（把点投影到线段方向，看比例 t 在不在 0～1）
2. `side(p, a, b)` —— 叉积判定所在一侧。正负代表两侧，`数值 / 线长` 为实际像素距离
3. 死区：`|s| / 线长 <= margin` 就跳过这一帧，既不计数也不更新记录
4. 查表 `prev_[(线序号, 车号)]` —— 上次在哪一侧
5. 符号变化即换边，即过线。再由 `count_dir` 决定是否计数
6. 不管数没数，都把这次的 `s` 写回表里

`count_dir` 的含义：

- `"pos"` = 只数「负侧 → 正侧」
- `"neg"` = 只数「正侧 → 负侧」
- 不写 = 两个方向都数

`retain(live_ids)` 每帧调一次，把跟踪器已经删掉的车号从 `prev_` 里清掉。不清的话接摄像头连跑几天会攒到几十万条。

### 十一、INT8 量化精度

同一份权重导出三个模型。评测集为验证集 1510 张（10795 个标注框）；输入为 RGB、letterbox 至 640；评估口径 conf=0.001、NMS IoU=0.7，单类，AP 按全点插值计算 mAP50 与 mAP50-95。

| 模型 | mAP50 | mAP50-95 | 每图框数（conf 0.001） |
|---|---|---|---|
| ONNX FP32 | 0.9426 | 0.7196 | 26.1 |
| RKNN FP16 | 0.9426 | 0.7191 | 26.2 |
| RKNN INT8 | 0.9037 | 0.6125 | 26.2 |

INT8 相对 FP32：mAP50 下降 3.9 个百分点（相对 4.1%），mAP50-95 下降 10.7 个百分点（相对 14.9%）。

损失集中于定位精度：坐标量化步长为 2.5 px，匹配框的中心平均偏移 1.86 px；检出能力基本不变，每图框数 26.1 → 26.2。FP16 与 FP32 在本口径下无可测差异（mAP50 相同，mAP50-95 差 0.0005），可视为无损。

### 十二、网页监控台

同一套算法，多一个能远程看的入口。

`traffic_count` 是给个配置就跑到底、跑完退出；`traffic_web_single` 是起来之后蹲在那，等网页下命令。浏览器里选配置、点开始、拖参数、看画面和过车记录，不用碰命令行。

三个可执行文件共用 `config.cpp` / `counter.cpp` / `tracker.cpp` / `detector.cpp`，网页版只多一个 `web_server.cpp`（HTTP + MJPEG 推流）。计数、跟踪、推理一行都没复制。`traffic_web_single` 管一路，`traffic_web_quad` 管四路（见十二点五）。

#### 页面上有什么

| 区域 | 功能 |
|---|---|
| 顶栏 | 选配置（自动扫 `configs/*.json`）、开始 / 暂停 / 重新开始 / 停止 |
| 主画面 | MJPEG 实时画面。服务端画好再推，不是前端叠图 |
| 图层 | 检测框 / 跟踪编号 / 计数线与数字 / 检测区域，四项独立开关 |
| 参数 | `conf`、`iou` 两个数字框，改完立即生效 |
| 系统状态 | CPU 占用、温度、NPU/GPU 频率、NPU 三核负载 |
| 计数 | 每条线各自的数字、当前跟踪数、fps、单帧耗时 |
| 过车记录 | 最近 40 条，带抓拍图，点图看大图，Esc 关闭 |

运行中切换配置不用先停止：选另一路点「切换」，旧会话销毁、计数归零、画面直接换掉。视频播完停在最后一帧，状态转暂停，点「重新开始」重跑一遍。

#### 参数改动的边界

网页上改的只写进内存，`configs/*.json` 一个字节都不动，进程重启就回到 json 的值。

| 参数 | 网页能改 | 原因 |
|---|---|---|
| `conf` | 能 | 改变后重建 Detector，约两三百毫秒 |
| `iou` | 能 | 同上 |
| `imgsz` | 不能 | 影响模型输入尺寸，重建代价大 |
| `roi` / `lines` | 不能，只能开关显示 | 改要重建 `Counter`，计数会清零 |
| `draw` 的颜色、线宽 | 不能，只能开关显示 | 属于配置，不属于运行时参数 |

启动一路时先用 json 里的 `detect.conf/iou` 当初始值，保证网页版和 `traffic_count` 跑出来的数字一致；之后网页改才覆盖它。

#### HTTP 接口

全部是 GET，可以直接 curl 测。

| 端点 | 作用 |
|---|---|
| `GET /` | 页面 |
| `GET /stream` | MJPEG 推流 |
| `GET /api/configs` | 列出 `configs/*.json` |
| `GET /api/state` | 各线计数 / 跟踪数 / fps / 当前参数 |
| `GET /api/events` | 最近 200 条过车记录 |
| `GET /snap/<文件名>` | 抓拍小图 |
| `GET /api/start?config=test1` | 开始，或运行中切换到这一路 |
| `GET /api/pause?on=1` | 暂停 / 继续 |

#### 抓拍图

存 `output/snapshots/`，命名 `帧号_线名_序号.jpg`，128×128，只画一个检测框，不画计数线和编号——记录里只需要看清是哪辆车。

过线记录里的坐标就是框中心，抓拍时按中心最近的那个 track 定位，所以不会抓错车。

#### 线程模型

- 一个 accept 线程；每个浏览器客户端一个 detached 线程
- 推流线程靠条件变量等新帧，不空转，也不占着锁写网络
- 主线程跑推理循环；网页的开关、参数通过 `atomic` 变量传进去
- 没有第三方 HTTP 库，`web_server.cpp` 里用 POSIX socket 自己写的
- 客户端提前关页面时忽略 `SIGPIPE`，避免整个进程被打死

### 十二点五、四路分屏

一台板子同时跑四路视频，网页 2×2 分屏看，点某一路进详情页。计数、参数、图层各自独立。

#### 编译与启动

```bash
make traffic_web_quad
./traffic_web_quad 8081
```

只给端口。配置名默认 test1～test4，帧率默认跟源视频（12 / 30 / 24 / 8 fps）。老写法 `./traffic_web_quad 8081 test1 test2 test3 test4 20` 仍兼容，第 2 个数字参数是每路帧率上限。

后台常驻要用 `setsid`，`nohup ... &` 在非交互 shell 里会被回收：

```bash
setsid ./traffic_web_quad 8081 > /tmp/quad.log 2>&1 < /dev/null &
```

#### 线程分配

每路 2 个推理线程（`kInferPerCam = 2`），四路共 8 个，按 `(路号 × 2 + 槽位) % 3` 轮流绑到 NPU 的三个核上，所以四路能真正并行而不是抢一个核。另有每路 1 个读帧线程 + 1 个跟踪线程。

#### 接口都带 cam 路号

| 端点 | 作用 |
|---|---|
| `GET /` | 分屏页 |
| `GET /stream?cam=N` | 第 N 路 MJPEG（`&thumb=1` 是缩略图） |
| `GET /api/state?cam=N` | 第 N 路状态 |
| `GET /api/param?cam=N&conf=0.3&iou=0.3` | 改第 N 路参数 |
| `GET /api/restart?cam=N` | 第 N 路从头跑 |
| `GET /api/overlay?cam=N&box=1&id=0&line=1&roi=1` | 第 N 路图层开关 |
| `GET /api/start?config=all` | 四路一起开 |
| `GET /api/pause?on=1` | 全部暂停 / 继续 |
| `GET /api/quit` | 退出进程 |
| `GET /api/configs` | 列 `configs/*.json` 的文件名（不带后缀） |
| `GET /api/videos` | 列 `data/videos/` 下的视频文件 |
| `GET /api/source?cam=N&url=<地址>&config=<名>` | 给第 N 路换源换配置并启动 |
| `GET /api/source?cam=N&stop=1` | 停第 N 路，地址和配置保留 |

`/api/source` 只写字符串并把 `src_gen_[cam]` 加一，不动线程；主循环每轮比对版本号，发现变了就 `stop_one` → 重载配置 → 重新解析地址 → `start_one`。

`url` 前缀是 `rtsp:// rtsps:// http:// https://` 时按实时流处理（不控节奏、断流不清零计数、连不上按 2→4→6→8→10 秒退避重试），否则当本地文件（循环播放，每轮 epoch+1 清零计数）。

#### 网页上换视频源

监控台顶部「视频源」卡片，四行对应四路：

| 列 | 取值 |
|---|---|
| 类型 | 本地视频（下拉选 `data/videos/` 里的文件）/ 视频流（手填地址） |
| 配置 | `configs/*.json`，决定这一路的 ROI、计数线、跟踪阈值 |
| 接入 / 断开 | 起停这一路 |

交互规则：

- 运行中三个控件全锁死，只能点「断开」；断开后才放开
- 「断开」走 `/api/source?cam=N&stop=1`，只停线程，`source_[N]` / `src_cfg_[N]` 不清空。刷新页面这一行还在，再点「接入」就恢复原地址
- 状态圆点灰色「空闲」= `idle_[N] == true`；绿色「运行中 · N fps」= 在跑
- 四路可以任意组合，本地文件 / 视频流 / 空闲混着都行

#### 参数初值的来路

启动时每路先读自己的 `configs/testN.json`，把 `detect.conf` / `detect.iou` 灌进 `WebServer::init_params()` 当参数面板的初值；之后网页上改只动内存，`configs/*.json` 一个字节都不写，进程重开又回到 json 的值。

单路版用 `params_inited` 标志实现同样的事，四路版直接在配置加载循环里调 `init_params`。放在视频检查之前，这样某路视频缺失时面板上显示的仍是它的配置值。

#### 实测

四路各 20 fps 稳定，单帧推理 40～60 ms，进程占 487% CPU（8 核）。

卡顿的来源：4 条 MJPEG 常驻推流单条约 500 KB/s，四条合计约 2 MB/s；浏览器对同一主机只开 6 个并发连接，4 条流占满后状态轮询要排队，页面就越看越卡。首页本身不慢（13 KB，13～48 ms），状态接口 19～60 ms。治法有两个方向——降缩略图帧率或分辨率，或把轮询合并成一次请求——尚未做。

#### 视频流实测

PC 侧 MediaMTX 推 4 路 RTSP，板子拉流，四路同时跑：

| 视频 | 源帧率 | 板端 fps | 与本地文件比 |
|---|---|---|---|
| test1 | 12 | 12.0～12.5 | 持平 |
| test2 | 30 | 29.9～30.9 | 持平 |
| test3 | 24 | 23.8～24.0 | 持平 |
| test4 | 8 | 7.7～8.2 | 持平 |

RTSP 走 TCP（`-rtsp_transport tcp`）。H.264 是软解码，但板子只解码不编码，CPU 占用与本地文件模式相当，帧率没有损失。

日志降噪这块值得单独记一笔。OpenCV 的 `cv::utils::logging::setLogLevel` 只管 OpenCV 自己打的，管不到 libav。视频流连不上时 libavformat 每次重试都打一行 `[tcp @ 0x...] Connection to tcp://... failed: Connection refused`。做法是 `dlopen("libavutil.so")` 取 `av_log_set_callback` 换成空函数，且每次 `cap.open()` 之后再设一遍（OpenCV 的 ffmpeg 后端会把回调改回去）。不能直接链 `libavutil`：板子上只有运行库没有开发包，链了编不过。配合 2→4→6→8→10 秒退避，连不上的地址 25 秒内只打 1 行。
