# INT8 精度验证方案

> **状态：已执行（2026-10-22），结论见下方第一节。**
> 后面的章节是最初的实验设计，保留供复现。

目标：量化回答一个问题 —— **同一个模型转成 INT8 后，检测精度掉了多少**。
比较对象是三个模型在同一批图上的检测结果，不是看谁跑得快。

---

## 〇、结论（2026-10-22 实测）

验证集 1510 张（10795 个标注框），口径 conf=0.001、NMS IoU=0.7，单类。

| 模型 | mAP50 | mAP50-95 | 每图框数 |
|---|---|---|---|
| ONNX FP32 | 0.9426 | 0.7196 | 26.1 |
| RKNN FP16 | 0.9426 | 0.7191 | 26.2 |
| RKNN INT8 | 0.9037 | 0.6125 | 26.2 |

**三点结论：**

1. **INT8 的损失全在定位精度**：mAP50 降 3.9 点，mAP50-95 降 10.7 点，但每图框数不变（26.1 → 26.2）
   —— 说明检出能力没退化，是框画歪了。

2. **FP16 与 FP32 无可测差异**，可视为无损。

3. **框歪的程度**：当时测得坐标量化步长 2.5 px，匹配框中心平均偏移 1.86 px（640 空间）。
   折原图约 6.75 px。

> **第 3 条已于 2026-11-02 修复**：中心偏移从 6.75 px 降到 0.03 px，速度不变。
> 方法见 [`head4_原理详解.md`](head4_原理详解.md)。

## 一、三个被比较的模型

| 编号 | 模型 | 来源 | 送进去的数据格式 |
|---|---|---|---|
| A | ONNX FP32 | `models/best_detrac.onnx`，onnxruntime 跑 | NCHW float32，RGB，0~1 |
| B | RKNN FP16 | 同进程 `build(do_quantization=False)` | NHWC float32，RGB，0~1 |
| C | RKNN INT8 | 同进程 `build(do_quantization=True, dataset=校准数据)` | NHWC float32，RGB，0~1 |

- B 的作用是**对照组自检**。C++ 版 README 里已经实测过 fp16 与 ONNX 输出完全一致（同一帧 143 框、坐标对到小数点后一位）。
  如果这轮 B 和 A 差出明显数字，说明评估代码本身有问题，先修代码，别急着看 C。
- **C 的输入格式定为 float32 0~1，不改动任何 C++ 代码**。理由：`rknn_detector.cpp` 现在送的就是
  `RKNN_TENSOR_FLOAT32` + `blobFromImage(1/255)`，保持同一约定，上板时一行代码都不用动。
  代价是板端每帧多一次 float→int8 转换、输入张量 **4.9 MB 而不是 1.2 MB**（640×640×3，float32 vs uint8），
  相对卷积计算这点开销单路可以接受，多路并发时会成负担。注意：**这不影响精度**，同一个量化 scale 下
  喂 float 0~1 和喂 uint8 0~255 数学等价，差的是搬运和转换开销。
- C 是唯一新增的东西，难点全在它身上。

## 二、数据

| 用途 | 目录 | 数量 | 有没有标注 |
|---|---|---|---|
| 评测 | `data/dataset` 的 `val.txt` | 1510 张里按固定步长抽 **300 张** | 有（YOLO 格式，单类 vehicle） |
| 校准 | `data/aicity/images` | 465 张里抽 **150 张** | 无（也不需要） |

理由：
- 评测必须有标注，否则算不出 mAP。
- 校准图要求独立来源，不能和评测集同源，否则 INT8 的量程专门为这批图调过，结果偏乐观。
  aicity 既没参与训练也没参与评测，符合条件；它没标注，正好只干校准这一件事。
- `val.txt` 里是 `D:/...` 绝对路径，WSL 里解析不到，脚本内部统一转成 `/mnt/d/...`。
- **校准数据的格式**：150 张按第三节预处理成 0~1 的 float32，存成一个 `.npy`（形状 `N×640×640×3`）。
  因为 C 的输入是 float 0~1，校准统计必须落在同一个尺度上，否则量程跑偏。
  这一步能不能成，取决于 `build(dataset=...)` 认不认 npy —— 认不了就按第九节的后备方案走。

## 三、预处理（三个模型必须完全一致，否则比出来的差异不是量化造成的）

1. 读图 → BGR 转 RGB（YOLOv8 训练时用的就是 RGB）
2. letterbox 到 640：等比缩放 + 114 灰边补齐（不是拉伸，保持长宽比）
3. 标注框做同一套变换：归一化 xywh → 原图像素 → 缩放 → 加边偏移，落到 640 空间
4. 不裁 ROI：UA-DETRAC 这批图没有 ROI 配置，整图送入
5. 两类图尺寸不同（UA-DETRAC 960×540，aicity 1920×1080），letterbox 后统一是 640×640

## 四、评估算法（mAP 怎么算出来）

1. 模型输出 `[1,5,8400]`，转成 8400×5：cx、cy、w、h、score
2. **conf 阈值取 0.001**，全部框保留。mAP 依赖完整排序，不能像部署那样卡 0.1
3. NMS，`iou=0.7`（与 ultralytics 验证时的默认值一致，便于和已有的 mAP50 0.908 对照）
4. 每张图：框按分数从高到低，依次与未匹配的标注框比 IoU，≥0.5 记命中（TP）；同一标注只认一次，重复的算误检
5. 汇总全部 TP/FP/FN → 画 P-R 曲线 → 曲线下面积 = AP50
6. IoU 从 0.5 到 0.95 每隔 0.05 重算一遍取平均 = AP50-95
7. 三个模型各走一遍同一套代码，保证口径一致

## 七、怎么跑、要多久

在 WSL 的 rknn 环境（该环境已有 onnxruntime 1.23.2）：

```
source ~/rknn_env.sh
cd /mnt/d/multi-road-crossing-vehicle-count
python tools/eval_int8_precision.py
```

耗时预估：fp16 build 3~5 分钟，INT8 build（带 150 张校准）5~10 分钟，ONNX 跑 300 张约半分钟，
两个 RKNN 模拟器各跑 300 张（每张 1~2 秒）约 10~20 分钟。**总计 30 分钟内**。
模拟器速度慢是正常的，不代表板端。

## 八、必须写进结论的局限（不写就是给自己挖坑）

1. 跑的是 RKNN-Toolkit2 的 **PC 模拟器**，软件逐层仿真。它能说明量化误差的量级，**不等于板端真机表现**；速度数字毫无参考价值。
2. `val.txt` 那 1510 张是训练时每轮都在验证的集，不是全新测试集。**绝对值偏乐观，这轮只做三个模型之间的相对比较**，不代表泛化能力。
3. 校准图（aicity）与评测图（UA-DETRAC）来源不同，量程偏中立保守，不会让 INT8 显得更好。
4. 评估用 `iou=0.7`，部署配置是 0.5/0.6。**这个 mAP 只用来判断模型之间的差异，不代表部署时的计数精度**；计数误差要另外用 test3/test2 的 A/B 线数字衡量。
5. 本轮用 float32 输入，为的是不动 C++ 代码。**这不影响精度**，只多搬 3.7 MB/帧。以后上板做多路并发，把这刀砍掉（改 uint8）是纯性能收益。

## 九、风险与应对

| 风险 | 应对 |
|---|---|
| INT8 build 报算子不支持 | 记录完整报错；退到调 `optimization_level`，或指定某些层不做量化（混合量化） |
| **`build(dataset=...)` 不接受 npy 校准数据** | 退到后备方案：校准改回 jpg + `mean_values=[[0,0,0]] / std_values=[[255,255,255]]`，模型输入变成 uint8 0~255。代价是 `rknn_detector.cpp` 要改两行（`RKNN_TENSOR_UINT8`、blob 不除 255）。**改 C++ 之前一定先问你，不擅自动** |
| 输入格式嗅探不到合理输出（分数上万） | 单独打印首张图 top5 分数排查 mean/std 配置，不硬跑 |
| 模拟器耗时超预期（超过 1 小时） | 评测降到 150 张，重新出表，并在结论里注明张数 |
| fp16（B）与 ONNX（A）差得明显 | 停止，先查评估代码（NMS/坐标系/letterbox 偏移），不把问题当成量化损失 |
