## 1. 检测区域 ROI（裁剪）+ 助跑区　~~【优先级最高】~~　✅ 已完成 2026-10

### 做什么

摄像头是固定的，所以画面里哪些区域我们**根本不关心**（天空、楼房、绿化、远处）
可以事先定死。检测前先按这个区域把图裁出来，只把裁出来的部分送进模型。

### 为什么

**两个好处都有**，实测数据在文末。

1. **更准**：裁剪等于给中心区域"放大"。整张 1920×1080 送进模型会被压到 1280，
   车缩小 0.67 倍；裁成 960×960 再送进去是 1:1，车在网络里反而更大更清楚。
2. **更快**：裁小之后可以用更小的输入尺寸。

### 关键：区域必须包含"助跑区"

**这是最容易踩的坑。**

跟踪器要看到一辆车**连续好几帧**，才知道它"上一帧在线哪一侧"。
等车撞到计数线那一刻，才有"从一边到另一边"这个判断。

如果区域框得太紧，车刚进画面就到线上了——跟踪器没有它的历史，**这一辆就漏了**。

**经验值**：助跑区够车跑 1~2 秒。30 帧/秒就是 30~60 帧；
车一帧走 10 像素的话，要留 300~600 像素。

**画区域的原则**：计数线放在区域里**靠后**的位置，前面留足跑道。

### 顺带解决的

- 广告牌被认成公交车 → 广告牌在区域外，根本不会被检测
- 左上角、右边的车检不到 → 那些车本来就不关心，这是**主动不要**，不是"漏掉"

> 区别很重要：**漏掉是失控，不要是设计。**

## 2. 跳帧检测　【优先级高，省一半算力】

### 做什么

每 2 帧才做一次检测，中间那帧不检测，直接用跟踪器的**预测框**补上。

### 为什么

跟踪器每一帧本来就在**预测**车下一帧会在哪（它就是靠这个把 ID 接上的）。
既然它会预测，检测就没必要每帧都做。

速度直接翻倍，计数几乎不受影响（车的位置是连续的）。

**这一招对 RK3588 多路实时是救命的**，比堆硬件管用。

### 要注意

帧率低的视频（比如 12 帧/秒）跳帧后间隔变大，跟踪预测会不准。
按视频帧率决定跳几帧：30 帧/秒可以跳 1 帧，12 帧/秒就别跳了。

## 3. ID 断连接回（ReID）

### 做什么

车消失后**别马上忘掉它**，记着它最后的位置、长相、时间。
过几帧如果附近冒出一个新框、长得也像，就把旧编号还给它。

### 为什么

这是当前**计数偏多的最大来源**。车被挡住、或者漏检一帧，跟踪器就以为它走了；
下次出现发个新编号，同一辆车被算两次。

实测：test1 前 300 帧里出现过 51 个不同 ID，但同一时刻画面上只有 5~10 辆车。
多出来的就是断连产生的。

### 为什么这条对项目"含金量"最重要

ByteTrack 本身不做这件事。补上它就是**你自己的改进**，业界叫 ReID（重识别）。
简历和答辩上写这个，比写"跑通了 YOLOv8"有分量得多。

### 怎么做（由简到繁）

1. **最容易**：车消失后保留若干帧；新框出现时，如果位置和消失点离得近、大小也接近，就认成同一辆
2. **中等**：再加上"车身颜色"这个特征做辅助判断
3. **最复杂**：用专门的重识别模型提取外观特征（就是真正的 ReID）

**建议先做第 1 种**，改动最小，收益最大。

## 6. 人工基准对照　【答辩必备，建议早做】

### 做什么

挑一段 2~3 分钟的视频，**人工盯着数出真实过车数**，再和程序跑出来的数字对比。

### 为什么

没有这个，"准确度提升了"就是空口说白话，答辩一问就露馅。

而且它会告诉你**到底差多少**——差 5% 还是差 50%，改进方向完全不同：
- 差得少 → 微调就够了
- 差得多 → 说明是漏检或 ID 断连，得先解决那个

**这个必须早做，因为它是所有改进的衡量尺子。**

## 8. 多进口道 + 区域配对判转向　【影响计数结构】

### 现在的问题

现在的计数是"**一条横线切全场，靠 x 区间分车道**"。
这隐含假设：所有车朝同一个方向走、车道在图像上竖直排列。

**真实路口不成立**——四个进口道的车流互相垂直。

### 正确做法

- **每个进口道单独算**，东西南北各一套，互不干扰
- **线要垂直于车流方向**，不是图像上的水平线（南北向车流的计数线是竖的）
- **转弯不能混进直行**。正确做法不是靠单条线判转向，而是**区域配对**：
  把路口划成"西进口""北出口"等若干区域，车从"西进口"进、从"北出口"出 → 判为左转
  这叫虚拟线圈，是行业标准做法。单条线永远判不准转向。

配置文件的 `lines` 已经是个列表了，支持多条线；缺的是"线的方向命名"和"区域配对"。

# 实测数据（做过实验，别丢）

## 输入尺寸对检出数量的影响

同一张 1920×1080 的图（test4 第 60 帧），只统计汽车/公交/卡车：

| 做法 | 中心区检出 | 耗时（中位数） |
|---|---|---|
| 整图 → imgsz=640 | 21 辆 | 32 ms |
| 整图 → imgsz=960 | 25 辆 | 60 ms |
| 整图 → imgsz=1280 | 32 辆 | 103 ms |
| **裁中心960 → imgsz=640** | **31 辆** | **48 ms** |
| **裁中心960 → imgsz=800** | **37 辆** | **73 ms** |
| 裁中心960 → imgsz=960 | 37 辆 | 102 ms |

**读法**：

- 整图 @1280（32 辆 / 103 ms）≈ 裁960 @640（31 辆 / 48 ms）—— **精度一样，快一倍多**
- 裁960 @800（37 辆 / 73 ms）—— **多检出 16%，还快 30%**

## 另一组：只看检出数量

test4 同一张图：

| imgsz | 检出的车 |
|---|---|
| 640（YOLO 默认） | 29 辆 |
| 960 | 51 辆 |
| 1280 | 71 辆 |
| 1600 | 84 辆 |

**结论**：监控画面里车小，默认的 640 会漏掉一大半。

⚠️ **训练用什么尺寸，部署就必须用什么尺寸**，两边不一致精度会掉。
