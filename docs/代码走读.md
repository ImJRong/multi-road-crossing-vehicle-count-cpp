# 代码走读

命令行版、单路网页版、四路网页版共用一条链路。三者真正的差别在最后一步：谁来组织这些环节，是串行到底，还是拆成几条流水线。

## 一、全局：一帧数据是怎么走完的

```
读视频帧（OpenCV）
   ↓
裁 ROI 外接矩形          ← 只把感兴趣的区域送进模型，裁小等于放大
   ↓
letterbox 到 640×640      ← 等比缩放 + 四周补 114 灰边
   ↓
NPU 推理（rknn_detector） ← 输出 8400 个候选框的分数和坐标
   ↓
分数过滤 + NMS            ← 留下互不重叠的若干个框
   ↓
坐标还原                  ← 减补边、除缩放比、加回 ROI 偏移 → 整图坐标
   ↓
跟踪（tracker）           ← 给每个框发稳定编号，跨帧保持同一辆车同一个号
   ↓
静止目标过滤              ← 只把"真的在动"的送去计数
   ↓
穿线计数（counter）       ← 同一个号从线的这侧跑到那侧，计数 +1
   ↓
画框、画线、写数字 → 显示或推流
```

链路上有两处坐标变换，漏了也不报错，只是结果全错。letterbox 补的灰边要留下偏移量 `dx`/`dy`，还原时得减回去；ROI 裁剪会让模型输出裁剪图坐标，而计数线和多边形都是整图坐标，中间差一个 `roi_rect` 平移。两处任缺一处，后面的几何判断全错，画面却看不出问题——框还是画在车上，只是位置系统对不上。

三个入口的差别集中在最后一步：

| 入口 | 线程结构 | 用途 |
|---|---|---|
| `main.cpp` | 单线程串行 | 命令行跑单个视频、存 mp4 |
| `web_main_single.cpp` | 单线程串行（读帧→推理→跟踪→画图） | 网页看单路实时画面 |
| `web_main_quad.cpp` | 四份上面那套，共享一个 WebServer | 四路分屏监控台 |

代码顺序大致就是数据流的顺序：先入口，再推理后端，再跟踪和计数，最后是网页版和几个旁路工具。取舍速查表放在末尾，按问题查比较快。

## 二、main.cpp —— 命令行入口

363 行，摊开只有三块：路径解析、画图、主流程。

### 2.1 编译期常量

```cpp
const std::string kRoot = TRAFFIC_PROJECT_ROOT;
const std::string kModel = TRAFFIC_MODEL;
```

两个值都由 CMake 在编译时灌进来（`CMakeLists.txt` 里的 `TRAFFIC_PROJECT_ROOT`）。路径写死、不读环境变量，理由很实际：板子上只有这一个部署位置，运行时再配置只是多一个能出错的地方。

`TRAFFIC_MODEL` 按 `USE_RKNN` 分两支（`src/main.cpp:48-54`）：开了指向 `.rknn`，关着指向 `.onnx`。两种后端共用同一份权重，区别只在文件格式。

### 2.2 三个路径函数

`resolve_config_path`（`src/main.cpp:71-76`）把命令行参数变成配置文件路径，认三种写法。

| 输入 | 结果 |
|---|---|
| `test3` | `<根>/configs/test3.json` |
| `test3.json` | `<根>/configs/test3.json` |
| `/tmp/mine.json` | 原样使用 |

判断依据只有一条：含不含斜杠。含斜杠当完整路径，不含就当配置名，再按有没有 `.json` 后缀补齐。

`resolve_video_path`（`src/main.cpp:104-121`）面对的是一个具体麻烦。json 里写的是相对路径（如 `data/videos/test3.mp4`），为的是整个项目文件夹拷到任何机器都不用改配置。可"相对"到底相对谁——工作目录、配置文件所在目录、工程根目录，三种都说得通。于是四个候选依次试，哪个能真正打开用哪个：

```cpp
const std::string candidates[] = {
    video,                    // 1. 相对当前工作目录
    cfg_dir + video,          // 2. 相对配置文件所在目录
    kRoot + "/" + video,      // 3. 相对工程根目录（实际最常用）
    cfg_dir + "../" + video,  // 4. 配置文件目录的上一级
};
for (const auto& c : candidates) {
  if (video_ok(c)) return c;
}
```

`video_ok`（`src/main.cpp:96-99`）用"真打开一次"而不是"查文件存在不存在"。路径拼对了但文件是坏的，这里同样返回 false。

### 2.3 画图的两个函数

`draw_tracks`（`src/main.cpp:136-153`）画框和编号。编号写成 `#12` 这种格式，作用不在好看，而在肉眼校验跟踪——同一辆车如果每帧换号，问题一眼就看出来。

`draw_counters`（`src/main.cpp:157-197`）画计数线和数字，里面有一段避让逻辑：几条线的数字压在一起时自动下移。

```cpp
for (int k = 0; k < 6; ++k) {
  cv::Rect box(tx, ty - ts.height, ts.width, ts.height + 4);
  bool clash = false;
  for (const auto& q : placed) {
    if ((box & q).area() > 0) { clash = true; break; }
  }
  if (!clash) break;
  ty += ts.height + 6;
}
```

`k < 6` 是硬上限，防死循环。文字在图上最多挪六行，挪不开就叠着。

### 2.4 主流程

八个阶段，代码里有对应的 `--- 1. ---` 到 `--- 8. ---` 注释。

阶段 3 算 ROI（`src/main.cpp:238-253`）是理解整条链路的关键。配置里的 ROI 是一个多边形，代码却算出两个东西：

```cpp
poly = to_cv_poly(cfg.roi);                              // 多边形，用来筛框中心
roi_rect = cv::boundingRect(poly) & cv::Rect(0, 0, width, height);  // 外接矩形，用来裁图
if (roi_rect.width <= 0 || roi_rect.height <= 0) { ... }  // 配置写歪了退回整帧
```

两个东西各管一段。外接矩形比多边形大，裁图只能用矩形（OpenCV 不支持裁多边形）；可裁完的矩形四角有些落在区域外，阶段 7.3 得用多边形再筛一次：

```cpp
if (!poly.empty()) {
  dets.erase(std::remove_if(dets.begin(), dets.end(),
                            [&](const Detection& d) {
                              const cv::Point2f c(...);
                              return cv::pointPolygonTest(poly, c, false) < 0;
                            }),
             dets.end());
}
```

筛的是**框中心**，不是整个框。一辆车边缘伸出区域外很正常，中心在区域内就算数。

阶段 7.2 的坐标还原（`src/main.cpp:287-293`）只有四行，可漏掉就全乱：

```cpp
for (auto& d : dets) {
  d.x1 += roi_rect.x;  d.x2 += roi_rect.x;
  d.y1 += roi_rect.y;  d.y2 += roi_rect.y;
}
```

模型在裁剪图上工作，返回裁剪图坐标。不把 `roi_rect` 的偏移加回去，后面的计数线和 ROI 多边形全对不上——那些都是整图坐标。

阶段 7.4 的静止目标过滤（`src/main.cpp:307-322`）决定计数准不准：

```cpp
const auto tracks = tracker.update(dets);
std::vector<TrackView> live;
for (const auto& tr : tracks) {
  if (tr.moving) live.push_back(tr);        // 只把真的在动的送去计数
}
for (const auto& tr : live) {
  const cv::Point2f c = center_of(tr.box);
  counter.update(tr.id, Point{c.x, c.y}, "vehicle", frame_no);
}
counter.retain(tracker.live_ids());         // 跟踪器删掉的 id，计数器也清掉
```

不加 `moving` 过滤会怎样：红绿灯、路牌、被风吹的广告牌，框在计数线上来回抖，每抖一次记一辆车。这也是 `kMinTravel`（默认 35 像素）不能设太大的原因——设大了，刚进画面的慢车还没攒够位移，就永远不算数。

`counter.retain` 那行不起眼，作用是防内存泄漏。跟踪器删掉某个编号后，计数器里"它上次在线哪一侧"的记录就没用了；不清的话，接摄像头跑几天能攒到几十万条。

收尾（`src/main.cpp:344-357`）除了打印统计，还写一份 csv：

```cpp
write_records(std::string("output/records_") + cfg.name + ".csv", counter);
```

这份 csv 只有一个用途：和 Python 版跑同一段视频，两个 csv 对拍，看计数差在哪。字段格式与 Python 版完全一致（`line,group,class,frame,x,y`），见 `src/recorder.hpp:14-27`。

## 三、推理后端

### 3.1 detection.hpp —— 为什么单独一个头文件

`src/detection.hpp` 只有 16 行，一个 `Detection` 结构体。单拎出来的理由写在文件头（`src/detection.hpp:3-7`）：

> ONNX 版和 RKNN 版是两个互斥的头文件，`main.cpp` 只会包含其中一个。但 `tracker.hpp` 也要用 `Detection` —— 如果它去包含 `detector.hpp`，板子上（用 RKNN）就会连带把 ONNX Runtime 的头文件拉进来，直接编不过。

典型的依赖倒置：最基础的数据结构放在无依赖的层，谁都来拿，自己不带任何后端。

### 3.2 detector.cpp —— PC 上的 ONNX Runtime 后端

126 行，一个 `detect()` 方法，四步。

letterbox 那段（`src/detector.cpp:34-56`）解决的是形状不匹配：模型只吃 640×640 方图，输入却是 1280×960 长方形。直接拉伸会让车变形，长宽比一乱精度就掉，所以走"等比缩放 + 四周补灰边"：

```cpp
const double scale = std::min(imgsz_ / static_cast<double>(frame.cols),
                              imgsz_ / static_cast<double>(frame.rows));
const int nw = static_cast<int>(std::round(frame.cols * scale));
const int nh = static_cast<int>(std::round(frame.rows * scale));
cv::resize(frame, resized, cv::Size(nw, nh));
const int dx = (imgsz_ - nw) / 2;   // 左右各补一半，记录偏移
const int dy = (imgsz_ - nh) / 2;
cv::Mat canvas(imgsz_, imgsz_, CV_8UC3, cv::Scalar(114, 114, 114));
resized.copyTo(canvas(cv::Rect(dx, dy, nw, nh)));
```

`dx`/`dy` 必须留着，把框坐标还原回原图时要先减掉这个偏移。

读输出那段（`src/detector.cpp:70-78`）的下标顺序是最容易错的一处，注释专门写了：

> 输出是 `[1, 5, 8400]`，内存里按行排：同一个属性的 8400 个值连在一起。所以取第 i 个框的第 j 个值，下标是 `j * 8400 + i`，不是 `i * 5 + j`。下标顺序写反会读出无意义的数值。

```cpp
const double cx = out[static_cast<size_t>(0) * n_cols + i];  // 不是 out[i*5 + 0]
```

NMS（`src/detector.cpp:109-125`）处理的是另一件事：同一辆车模型会给好几个稍微错开的框，只留最好的一个。做法是按分数从高到低排，依次取，和已留下的比，重叠超过阈值就丢：

```cpp
std::sort(boxes.begin(), boxes.end(),
          [](const Detection& a, const Detection& b) { return a.score > b.score; });
std::vector<Detection> keep;
for (const auto& b : boxes) {
  bool drop = false;
  for (const auto& k : keep) {
    if (k.cls == b.cls && iou(b, k) > iou_) { drop = true; break; }
  }
  if (!drop) keep.push_back(b);
}
```

只和同类比（`k.cls == b.cls`），不同类别不互相压制。这里是 O(n²) 朴素实现，没用 `cv::dnn::NMSBoxes`——分数过滤后的候选框通常只剩几十个，自己写反而更可控。

### 3.3 rknn_detector.cpp —— 板端 RKNN 后端

464 行，整个项目技术上最重的一个文件。前处理和后处理与 ONNX 版完全一致，只有四个调用换了（`src/rknn_detector.cpp:3-6`）：

```
Ort::Session   加载模型   ->  rknn_init
CreateTensor   提交输入   ->  rknn_inputs_set
session_.Run   执行推理   ->  rknn_run
GetTensorData  读取输出   ->  rknn_outputs_get
```

Impl 结构体（`src/rknn_detector.cpp:80-108`）用的是 PIMPL：把 `rknn_context` 这类 C 风格资源藏起来，头文件里只留一个 `std::unique_ptr<Impl>`。好处是 `rknn_api.h` 不用出现在头文件里，其它 .cpp 不必跟着包含。

NPU 三核（`src/rknn_detector.cpp:123-129`）在初始化时就开了：

```cpp
if (rknn_set_core_mask(impl_->ctx, RKNN_NPU_CORE_0_1_2) == 0) {
  VPRINT("NPU: 三核并行已开启\n");
}
```

RK3588 有三个 NPU 核，默认只用一个，这里默认开三核并行。调用方后面若用 `set_core()` 指定单核，会覆盖这个设置（`src/rknn_detector.cpp:278-294`）。四路网页版正是这么用的——八个推理线程按 `(路号 × 2 + 槽位) % 3` 摊到三个核上。

单输出与双输出分开的理由（`src/rknn_detector.cpp:15-25`），注释写得最清楚：

> 量化将整个张量映射到 8 位整数，同一张量共用一套 scale。坐标值域 0～640，分数值域 0～1，若共用步长 2.5，则 0.87 会被舍入为 0，导致分数全部失效、无法检出目标。拆分后 boxes 使用步长 2.5，scores 使用 1/255，各自独立，分数得以保留。

代码用"行数是否为 4"识别坐标输出（`src/rknn_detector.cpp:183-189`），不看输出顺序——顺序在转换版本之间会变。

head4 模型的识别与 anchor 表（`src/rknn_detector.cpp:224-271`）靠查输出张量名里有没有 `dfl`：

```cpp
impl_->boxes_is_dist = std::string(a.name).find("dfl") != std::string::npos;
```

命中说明模型输出的是 DFL 距离而不是坐标，得先建三张表：

```cpp
struct SegBlk { int n; int g; float stride; };
const SegBlk segs[3] = {{6400, 80, 8.f}, {1600, 40, 16.f}, {400, 20, 32.f}};
// 网格中心坐标 = (列号 + 0.5, 行号 + 0.5)
impl_->anchor_x[i] = static_cast<float>(k % s.g) + 0.5f;
impl_->anchor_y[i] = static_cast<float>(k / s.g) + 0.5f;
```

8400 = 6400 + 1600 + 400，对应三个尺度的输出特征图（80×80、40×40、20×20）。`k % g` 是列号，`k / g` 是行号。

head4 的坐标换算（`src/rknn_detector.cpp:400-424`）是整段后处理里唯一需要动脑子的地方：

```cpp
const double ax = impl_->anchor_x[idx];   // 网格中心 x
const double ay = impl_->anchor_y[idx];
const double st = impl_->stride_tab[idx];

const double l = coord[idx];                              // 左距离
const double t = coord[1 * n_cols + idx];                 // 上距离
const double r = coord[2 * n_cols + idx];                 // 右距离
const double b = coord[3 * n_cols + idx];                 // 下距离

x1 = (ax - l) * st;
y1 = (ay - t) * st;
x2 = (ax + r) * st;
y2 = (ay + b) * st;
```

这四行公式等价于被移除的 9 个 ONNX 算子（Slice×2 / Sub×2 / Add×2 / Div / Concat / Mul）。把换算从模型搬到 CPU，就是"框偏移"的全部解法——原来那 9 个算子跑在 INT8 量化模型里，中间结果的精度被量化刻度吃掉大半；搬到 CPU 用 float 算，精度回到理论值。

推导在 `docs/head4_原理详解.md`，结论是：距离张量的量化刻度 0.047，原模型坐标张量的刻度 2.502，相差 53 倍。

输入走 uint8 而不是 float（`src/rknn_detector.cpp:310-323`）：

```cpp
// 1.6.0 运行库处理 float32 输入时会段错误，因此使用 uint8 + NHWC，
// 即 RKNN 官方示例的标准做法：传入原始像素，归一化与布局转换由驱动完成。
inputs[0].type = RKNN_TENSOR_UINT8;
inputs[0].fmt = RKNN_TENSOR_NHWC;
inputs[0].pass_through = 0;   // 0 = 让驱动按上面两项做格式转换
```

这个写法由实测确定：传 float32 会触发段错误，所以传原始像素，归一化交给驱动。

输出反量化交给驱动（`src/rknn_detector.cpp:347-355`），两行即可：

```cpp
outputs[i].want_float = 1;
outputs[i].is_prealloc = 0;
```

`want_float = 1` 让驱动把 int8 直接反量化成 float 返回，后续不必处理量化参数。注释给了原因：手工反量化会和驱动的处理冲突。

性能统计（`src/rknn_detector.cpp:328-342`）用 `static` 局部变量累计，每 100 帧打一次平均：

```cpp
static double sum_in = 0.0, sum_run = 0.0;
static int cnt = 0;
if (++cnt % 100 == 0) {
  VPRINT("[PERF] 喂数据 %.2f ms | NPU 计算 %.2f ms | 合计 %.2f ms（上限 %.1f fps）\n", ...);
}
```

把"喂数据"和"NPU 计算"拆开统计，是为了定位瓶颈：喂数据慢说明卡在数据搬运，NPU 计算慢说明模型本身重。

静默宏（`src/rknn_detector.cpp:40-47`）是为四路版加的：

```cpp
namespace { bool g_verbose = true; }
void rknn_set_verbose(bool on) { g_verbose = on; }
#define VPRINT(...) do { if (g_verbose) std::printf(__VA_ARGS__); } while (0)
```

四路网页版有 8 个 detector，每个初始化打一串日志能把终端刷满，所以进程启动时统一关掉。

## 四、跟踪

### 4.1 kalman_track.hpp —— 卡尔曼滤波

111 行，两件事：预测"这帧这条轨迹该在哪"、用检测框校正。

状态定义（`src/kalman_track.hpp:3-5`）是 8 维的：

```
状态 8 维：cx, cy, w, h, vcx, vcy, vw, vh
观测 4 维：cx, cy, w, h
```

前四个是框的位置和大小，后四个是它们每帧的变化量。检测框只给前四个，没人告诉它速度——速度是滤波器自己估出来的。

不自己写矩阵运算、直接用 OpenCV 自带的（`src/kalman_track.hpp:7-9`），理由只有一个：update 那一步要对 4×4 矩阵求逆，手写容易错一个符号就全崩。

噪声参数（`src/kalman_track.hpp:34-38`）是实测出来的，不是拍的：

```cpp
// 实测（test1 静止车 721 帧）：检测框中心抖动 σ≈0.8px，框宽抖动 2.7%
const float std_meas = 2.0f;        // 观测噪声(px)：实测 0.8，取 2 留余量
const float std_q = 2.0f;           // 过程噪声(px)：和观测同量级
const float std_vel = h / 160.0f;   // 速度误差
```

速度误差按框高度缩放（`h/160`），大车的绝对误差天然比小车大。

文件头还记了一条教训（`src/kalman_track.hpp:14-15`）：

> 上一次的写法 Q 给 1e-2、R 给 4，导致增益只有 0.05，输出每帧只往检测框挪 5%，严重滞后于真实车辆，匹配全断。

这是跟踪失效的典型症状：滤波增益太低，预测位置追不上真实位置，IoU 掉到阈值以下，编号就断。

init 那一步故意不做校正（`src/kalman_track.hpp:17-19`）：

> `cv::KalmanFilter` 刚构造时内部预测量是 0，这时候调 `correct` 会让 `statePost = K × 观测 = 0.2 × 真实坐标`，位置直接被压成五分之一。init 只把观测值写进 `statePost` 就完事。

`state()` 和 `pred()` 的差别（`src/kalman_track.hpp:93-97`）就在这一点上：

```cpp
const cv::Rect2f& pred() const { return pred_; }              // 校正前：预测位置，匹配时用
cv::Rect2f state() const { return kf_ ? to_rect(kf_->statePost) : pred_; }  // 校正后：融合结果，输出时用
```

匹配要用预测位置（那时还没看到这帧的检测框），输出要用校正后的状态（已经融合了检测框）。两者混用，状态就不一致。

### 4.2 tracker.cpp —— ByteTrack 两阶段关联

257 行，核心是一个 `update()`（`src/tracker.cpp:127-257`），七步：预测、按分数分堆、两轮关联、建新轨迹、标 Lost、清理、输出。

头一步是预测（`src/tracker.cpp:130-133`）：

```cpp
for (auto& t : tracks_) t.pred = t.kf.predict();
```

不预测就只能拿上一帧的位置去比。车开得快时框错开很远，IoU 掉到阈值以下，编号断。

第二步按分数把本帧的框分成高分堆和低分堆（`src/tracker.cpp:135-142`），低于 `low_thresh` 的直接丢。

然后是两轮关联（`src/tracker.cpp:188-201`）：

```cpp
associate(all_tracks, det_high, match_thresh_);   // 第一轮：所有轨迹 × 高分框，阈值 0.8
associate(left_track, det_low, 0.5);              // 第二轮：没配上的 Tracked × 低分框，阈值 0.5
```

两轮的区别不只是框的分数，阈值也不同：第一轮 0.8（相当于 IoU ≥ 0.2，比较宽松），第二轮 0.5（相当于 IoU ≥ 0.5，更严）。

第二轮为什么要用低分框（`src/tracker.hpp:11-13`）：

> 车被挡住时置信度会掉到 0.1～0.25，但位置还对得上。丢掉这些框等于直接断号，拿它和"刚才丢了的轨迹"比一次，位置吻合就能续上。

低分框为什么不能建新轨迹（`src/tracker.hpp:15-17`）：

> 低分框里混着树影、反光、广告牌边缘。让它们建轨迹，一帧能冒出十几个假 ID，这些假 ID 在计数线上抖一抖就是一串假计数。

第二轮只取 `Tracked` 不含 `Lost`（`src/tracker.cpp:195`）：`Lost` 的位置是推算的，拿它和低分框比容易配错。

匈牙利算法（`src/tracker.cpp:39-94`）是 Kuhn-Munkres 的经典 O(n³) 实现，用顶标收缩找增广路，保证全局最优。关键注释在 `src/tracker.cpp:37-38`：

> 匈牙利算法会为每一行配上一列（数学上称完美匹配），因此调用方需自行剔除代价超过阈值的配对，否则所有轨迹都会配上。

对应代码在 `src/tracker.cpp:182`：

```cpp
if (cost[r][c] > thresh) continue;   // 强制剔除：不够像的一律不认
```

`assign_min_cost`（`src/tracker.cpp:97-113`）是个包装：匈牙利算法要求行数 ≤ 列数，行多了就转置后再算。

建新轨迹的时候（`src/tracker.cpp:203-221`），只有高分框里没人认领的才建，而且还要过 `new_thresh_` 这道门。两轮都没配上的轨迹走另一条路（`src/tracker.cpp:223-229`）：`lost+1`，超过 `track_buffer_`（默认 30 帧）就在第七步删掉。

输出这一环有个决定后来改过（`src/tracker.cpp:239-247`）：

```cpp
// 输出框直接用卡尔曼滤波后的状态。
// 2026-11-01 删掉了这里的 EMA（0.6×旧 + 0.4×新）：它和卡尔曼重复平滑，
// 白白多 1~2 帧滞后，过线时刻被推迟，转弯车更容易漏计。

```

这是排查"转弯车漏计"时删掉的一段代码。EMA 和卡尔曼是两种平滑手段，叠在一起等于平滑两次，后果是框位置滞后——滞后让过线时刻推迟。转弯车在画面上停留时间短，推迟一两帧就可能整车过去了还没被记上。

`moving` 的判定（`src/tracker.cpp:245-246`）只有两行：

```cpp
const cv::Point2f d = center_of(t.box) - t.origin;
v.moving = cv::norm(d) >= kMinTravel;   // 离出生点够远才算在开
```

比的是"当前中心"和"出生时的中心"，不是和上一帧比。判据因此稳定，不会因为单帧抖动误判。

## 五、counter.cpp —— 穿线计数

98 行，整个项目逻辑最简单、也最容易出错的部分。

### 5.1 思路

> 不做"框和线有没有相交"的几何判断，而是看"框中心点相对这条线在左边还是右边"。同一个跟踪 ID 上一帧在一边、这一帧在另一边 = 它穿过去了。

选这个思路是为了稳健：框和线相交的判定对框大小敏感，车大车小会得出不同结论；中心点落在线的哪一侧，只是一个标量比较。

### 5.2 side()：叉积判方位

```cpp
inline double side(const Point& p, const Point& a, const Point& b) {
  return (b.x - a.x) * (p.y - a.y) - (b.y - a.y) * (p.x - a.x);
}
```

用叉积（行列式）而不是按情况分支，好处是横线、竖线、斜线同一个公式。文件里配了一个完整的数值例子：

```
线是 a=(390,140) -> b=(695,140)
b.x-a.x = 305, b.y-a.y = 0，所以公式简化成 side = 305 × (p.y - 140)
p=(500,100) -> 305 × (-40) = -12200  负数，在线的上方
p=(500,180) -> 305 × (+40) = +12200  正数，在线的下方
p=(500,140) -> 0                     正好压在线上
数值 12200 ÷ 线长 305 = 40，正好是点离线的真实像素距离
```

最后一句最容易被忽略：`side()` 返回的是"像素 × 线长"，不是像素。判死区时要先除以线长。

### 5.3 near_segment()：点在不在这条线段上

```cpp
const double t = ((p.x - a.x) * ax + (p.y - a.y) * ay) / len2;
const double slack = pad / std::sqrt(len2);
return t >= -slack && t <= 1.0 + slack;
```

做法是把点投影到线段方向上，得到一个比例 `t`：0 在起点、1 在终点、0～1 之间算在线段上、超出就是跑到延长线上了。

不用"比 x 坐标在不在 a.x～b.x 之间"的原因很直接：线可能是竖的、斜的，比 x 会算错。

这个函数也是"转弯车漏计"的嫌疑人，注释里自己标了（`src/counter.hpp:47-48`）：

> 车从线的端点外侧绕过去时，t 会跑到 0～1 之外，直接被判成"不在线段上"，这一次过线就不算数了。

到目前这个怀疑**既没有被证实也没有被证伪**。已验证的部分是：改好框偏移后，跟踪断号数下降了 34.3%（四个视频合计 2559 → 1680），但计数只净增 12 个，所以框偏移只解释了约三分之一的漏计。要彻底查清得给 `counter.cpp` 加逐帧轨迹日志，跑完和 csv 对账。

### 5.4 update()：六步判过线

```cpp
void Counter::update(long long track_id, const Point& p, const std::string& cls, int frame_no) {
  for (size_t li = 0; li < lines_.size(); ++li) {
    if (!near_segment(p, L.a, L.b, L.margin)) continue;   // 1. 在不在这段线上
    const double s = side(p, L.a, L.b);                    // 2. 在哪一侧
    if (len <= 0) continue;
    if (std::fabs(s) / len <= L.margin) continue;          // 3. 死区
    const std::pair<size_t, long long> key(li, track_id);  // 4. 查上次记录
    auto it = prev_.find(key);
    if (it != prev_.end() && ((it->second < 0) != (s < 0))) {  // 5. 符号变了
      const bool passed = s > 0;
      const bool skip = (L.count_dir == "pos" && !passed) ||
                        (L.count_dir == "neg" && passed);
      if (!skip) { /* 记一笔 */ counters_[li] += 1; }
    }
    prev_[key] = s;   // 6. 无论本次是否计数，都更新所在侧，供下一帧比较
  }
}
```

这几步里有几处细节，单看代码不容易发现。

死区（第 3 步）：`s` 是像素距离与线长之积，除以线长才得到像素距离。目标压在计数线上时框中心存在抖动，离线距离小于 `margin` 即视为仍在线上，跳过该帧——既不计过线，也不更新记录。注释说得很直白："不然车停在线上能把数字刷爆。"

第 5 步比较的是布尔值不是数值（`src/counter.cpp:38-39`）：

> 比较的是 `s < 0` 这个布尔值，不是比数值大小，所以 -12200 → -8000 不算过线（还在同一侧），而 -12200 → +500 才算。

`count_dir` 的作用（`src/counter.cpp:42-47`）：

```cpp
const bool passed = s > 0;   // true = 从负侧跑到正侧
const bool skip = (L.count_dir == "pos" && !passed) ||
                  (L.count_dir == "neg" && passed);
```

- 不配 `count_dir`：两个方向都数
- `"pos"`：只数从负侧到正侧的
- `"neg"`：只数从正侧到负侧的

实测配置里 test1 的两条线都是 `neg`，test2～4 是 A 线 `pos` + B 线 `neg`。这不是缺陷——四个视频拍的都是单行道，只数一个方向是对的。

第 6 步的位置很关键：`prev_[key] = s` 在 `if` 块外面，**不管这次数没数都要更新**。写进 `if` 块里，被 `count_dir` 跳过的那些就不更新记录，下一帧比较的基准还停在两帧前，会算错。

### 5.5 retain()：防止内存泄漏

```cpp
for (auto it = prev_.begin(); it != prev_.end();) {
  if (live.count(it->first.second) == 0) {
    it = prev_.erase(it);      // 这辆车已经不在跟踪器里了
  } else {
    ++it;
  }
}
```

两个细节：边遍历边删必须用 `erase(it)` 的返回值，写成 `for (...) { if (死) prev_.erase(it); }` 会崩——删完 `it` 就失效，再 `++` 是野指针，代码注释里标了。另外，活着的 id 由调用方传进来，不让 `Counter` 自己判断，因为 `Counter` 不该去猜跟踪器的缓冲期有多长，判断谁死了是跟踪器的事。

### 7.1 web_main_single.cpp —— 单路单线程主循环

519 行，**单线程**——主循环里读帧、推理、跟踪、画图、推流依次串行，一次一帧（`src/web_main_single.cpp:388-486`）。

| `kCmdRestart` | 用同一个配置名 `open_session` 重建，计数和事件全部归零 |

`params_inited` 这个标志（`src/web_main_single.cpp:305, 316-328`）是四路版 `init_params` 的设计原型：

"只有第一次启动才读配置"是有意为之：网页上把 conf 调到 0.45，再点"重新开始"，不该被打回配置文件的 0.3——那等于白调。

不是循环播放，而是停在最后一帧转暂停态。四路版不同——那边是循环播的（`epoch+1` 后重来）。

按源视频帧率控节奏（`src/web_main_single.cpp:470-486`）这一段：

### 7.2 web_main_quad.cpp —— 四路

648 行，单路版的四份复制 + 一个共享的 WebServer。

线程总数：每路 1 个读帧 + 2 个推理（`kInferPerCam = 2`，`src/web_main_quad.cpp:73`）+ 1 个跟踪，四路共 16 个，加上主线程和 WebServer 的监听线程。实测 `ls /proc/<pid>/task | wc -l` 是 68 个线程。

每路的推理线程为什么不能共用一个 detector（`src/web_main_quad.cpp:72` 的注释）：

```cpp
// 每路几个推理线程(每个线程一个独立 detector, RKNN context 不能多线程共用)
constexpr int kInferPerCam = 2;
```

RKNN 的 context 不是线程安全的，每个推理线程只能自己建一个。代价是内存，换来的是并行度。

分核策略（`src/web_main_quad.cpp:330`）：

```cpp
det->set_core((c.id * kInferPerCam + slot) % 3);
```

`c.id` 是路号，`slot` 是这一路的第几个推理线程。展开就是 0、1、2、3、4、5… 轮流分到核 0、1、2。规律是连续两个线程落到不同核，避免同一路的两个线程抢同一个核。

三个关键的数据结构（`src/web_main_quad.cpp:195-230`）：

```cpp
struct CamJob {              // 读帧线程 → 推理线程
  int64_t frame_no = 0;
  int epoch = 0;
  std::shared_ptr<cv::Mat> full;   // 整图(画框用)
  cv::Mat roi_img;                  // ROI 裁剪后的图(推理用)
};

struct CamRes {              // 推理线程 → 跟踪线程
  int64_t frame_no = 0;
  int epoch = 0;
  std::vector<Detection> dets;
  double infer_ms = 0.0;
  std::shared_ptr<cv::Mat> full;
};

struct Cam {
  std::deque<std::shared_ptr<CamJob>> q_in;      // 待推理队列
  std::map<int64_t, CamRes> q_done;              // 已完成，按帧号作钥匙
  std::atomic<int> epoch{0};                     // 播完一轮 +1，跟踪线程看到就清空计数
};
```

`q_done` 用 `std::map` 而不是 `std::deque`，因为推理线程并行跑，完成顺序不等于帧号顺序。用帧号作钥匙，跟踪线程每次查 `q_done.count(next_no)`，就能按序处理。

`epoch` 的作用：视频播完一轮后 `epoch+1`（`src/web_main_quad.cpp:305`），跟踪线程发现 `epoch` 变了就重建跟踪器、清空计数（`src/web_main_quad.cpp:399-413`）。循环播放时每轮因此都是独立的。

暂停的处理要三处都做，缺一处就卡死。读帧线程暂停时连视频都不读（`src/web_main_quad.cpp:265-269`）；推理线程必须在"取 job 之前"判断暂停（`src/web_main_quad.cpp:340-345`），注释解释了原因：

> 取了再扔等于丢帧，跟踪线程会一直等一个永远不来的帧号 → 卡死。

跟踪线程同样在取结果之前判断（`src/web_main_quad.cpp:415-420`）。

从暂停恢复必须重新计时（`src/web_main_quad.cpp:270-276`）：

```cpp
// 从暂停恢复: 重新计时. 否则 sleep_until 的目标时间都已过去,
// 会一路狂奔补帧, CPU 飙满、fps 显示乱跳.
if (was_paused) {
  was_paused = false;
  t_start = std::chrono::steady_clock::now();
  n = 0;
}
```

这段是后来补的修复。原来的写法在暂停一分钟再恢复时，`sleep_until` 的目标时间全成了过去时刻，程序会连续不睡直接冲出去补上一分钟的帧，CPU 瞬间打满。

丢帧兜底（`src/web_main_quad.cpp:428-436`）：

```cpp
if (!c.q_done.count(next_no)) {
  // 等不到这一帧: 可能是被队列上限挤掉了(暂停恢复时最常见).
  // 连续等 1 秒还是没有, 就跳到队列里最小的帧号, 绝不卡死.
  if (++miss >= 5 && !c.q_done.empty()) {
    next_no = c.q_done.begin()->first;
    miss = 0;
  }
  continue;
}
```

另一个后补的修复。原来没有这段，某一帧一旦被 `while (c.q_done.size() > kQueueDepth*2) c.q_done.erase(...)` 挤掉，跟踪线程就永远等不到那个帧号，整路卡死。

`init_params` 的调用位置（`src/web_main_quad.cpp:560-565`）：

```cpp

server.init_params(i, static_cast<float>(c.cfg.detect.conf),
                   static_cast<float>(c.cfg.detect.iou));
c.video_path = resolve_video_path(c.cfg.video, cfg_path);

```

放在视频检查之前，这样某路视频缺失时面板显示的仍是它的配置值。这是最后一个修的功能点。

### 7.3 web_server.cpp —— HTTP 服务 + MJPEG 推流

580 行，没有用任何 Web 框架，直接 socket 编程。

架构：一个 accept 线程 + 每个客户端一个 `std::thread`（`detach` 出去）。MJPEG 是长连接，客户端断开靠写失败来发现。

`push_frame` 的节流（`src/web_server.cpp:141-148`）：

```cpp
const bool need_full = full_viewers_[cam].load() > 0;
const bool need_thumb = thumb_viewers_[cam].load() > 0;
if (!need_full && !need_thumb) return;
```

没人看这一路就什么都不做，连 JPEG 编码都省掉。这是四路能跑到 20 fps 的前提——四路都有人看时，每帧要编 8 张 JPEG（4 全图 + 4 缩略图）。

缩略图（`src/web_server.cpp:159-174`）宽度压到 `kThumbWidth = 480`，插值用 `cv::INTER_AREA`（缩小时质量最好）。

`sample_sys`（`src/web_server.cpp:180-236`）读 `/proc/stat` 算 CPU 占用率，读 sysfs 拿温度和 NPU 频率。用两次采样的差值算，因为 `/proc/stat` 给的是累计值。

`init_params`（`src/web_server.cpp:300-306`）：

```cpp
void WebServer::init_params(int cam, float conf, float iou) {
  if (cam < 0 || cam >= kMaxCams) return;
  if (conf > 0.0f) conf_[cam].store(conf);   // 配置里漏写(<=0)就保留默认值
  if (iou > 0.0f) iou_[cam].store(iou);
}
```

单开一个函数而不复用 `/api/param` 的解析逻辑，两个理由：float→string→float 绕一圈没必要；不想让 HTTP 解析路径沾上初始化。

conf/iou 为什么必须重建 detector（`src/web_main_quad.cpp:324`）：

```cpp
// 参数变了就重建 detector(RKNN 的 conf/iou 是建的时候定死的)
```

RKNN 的阈值在建 context 时就定死了，运行中改不了，只能销毁重建。代价是改一次参数要重新 `rknn_init` 一次，大约几百毫秒。

## 八、三个工具

### 8.1 rknn_probe.cpp —— 模型体检

判断一个 `.rknn` 模型能不能用。用法：`./rknn_probe models/X.rknn data/videos/test1.mp4 200`（跑到第 200 帧）。

核心是两种读法对比（`src/rknn_probe.cpp:195-215`）：`want_float = 1` 和 `want_float = 0` 各读一遍，打印统计量。判据就这几个数：

| 现象 | 含义 |
|---|---|
| boxes float 均值约 182 | 正常（head3） |
| boxes float 均值约 330 | 量化塌陷 |
| scores 里 `==zp(-128)` 约 8340 | 正常 |
| `==zp(-128)` 是 8400 | 分数全部失效 |

### 8.2 multi_eval.cpp —— 多路批量评测

每路一个线程，按 `i % 3` 绑 NPU 核，不画图不存视频，只统计计数。用来批量跑多个视频，或者测多路并行的吞吐。实测四路并行 71 fps，接近线性扩展。

### 8.3 pipeline_bench.cpp —— 流水线性能测试

单视频的流水线基准，参数 `--workers / --frames / --buf / --realtime / --no-track / --model`。两个用途：

- 测吞吐：`--workers 10 --buf 64` 得 118 fps，用来找拐点
- 测实时性：`--realtime 30` 按 30 fps 的节奏送帧，用来判断"接 30 fps 摄像头跟不跟得上"。判据不是吞吐而是**队列占用率**——队列一直是空的就说明跟得上

## 九、设计取舍速查表

散在各节里的决定收在一处，以后要推翻哪条，方便先看当初的理由。

| 决定 | 理由 |
|---|---|
| 检测头拆成输出 DFL 距离，CPU 换算 | INT8 量化把中间结果精度吃了 53 倍，搬出模型就绕开了 |
| 分数单独一路输出 | 坐标 0～640 和分数 0～1 共用 scale 会让分数全变 0 |
| 输入用 uint8 + NHWC 而不是 float32 | 1.6.0 运行库处理 float32 输入会段错误 |
| 跟踪输出用卡尔曼状态，不叠 EMA | 平滑两次 = 多 1～2 帧滞后 = 转弯车漏计 |
| 低分框只能救旧轨迹，不能建新轨迹 | 低分框里混着树影反光，建轨迹会刷出假 ID |
| 计数用"中心点在线的哪侧"而不是"框和线相交" | 框大小会影响相交判定，中心点只比标量 |
| `prev_` 不管数没数都更新 | 否则被 `count_dir` 跳过的帧会让下次比较用错基准 |
| 每个推理线程独立 detector | RKNN context 不是线程安全的 |
| `q_done` 用 `map` 不用 `deque` | 推理并行完成，顺序不等于帧号顺序 |
| 四路用 2 个推理线程而不是 1 个或 4 个 | 1 个跟不上 20 fps，4 个抢核且吃内存 |
| 配置里的 conf/iou 只灌进内存不写回 | 配置是底盘，页面改动是临时覆盖 |
| 自写 JSON 解析不引第三方库 | 板子上只为读一个小配置不值得 |
| `Detection` 单独一个头文件 | 避免 `tracker.hpp` 把 ONNX Runtime 头文件拉到板端编译里 |
